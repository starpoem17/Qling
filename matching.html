Qling Experience-based Matching 알고리즘 문서

작성일: 2026-06-04 / 기준: matching.md, docs/PRD.md, 실제 구현 코드

운영 반영 완료

1. 알고리즘 목적

Qling의 매칭 목표는 단순히 관심사가 비슷한 사람을 연결하는 것이 아니라, 비슷한 경험을 했거나 해당 고민에 답변할 근거가 있는 사용자에게 고민을 전달하는 것이다. MVP에서는 별도 추천 모델을 학습하지 않고, Firestore에 저장된 사용자 경험 프로필과 LLM 분석 결과를 조합해 매칭한다.

Firestore 사용자 데이터 + LLM Concern Analyzer + Experience Profile + Tier-based Retrieval + LLM Matching Judge + Post-processing Rule = 최종 Delivery Recipient

2. 전체 처리 흐름

1. 사용자가 온보딩에서 답변 가능한 주제 선택 2. 서버가 users.profileStatus, users.experienceProfile 초기화 3. 사용자가 고민 작성 4. 기존 moderation + category inference 실행 5. Concern Analyzer가 고민을 experience ontology로 분석 6. high risk면 delivery 없이 차단 7. 전체 후보 users를 eligibility policy로 필터링 8. experience profile과 concern tag overlap으로 retrieval score 계산 9. score와 profileStatus 기준으로 Tier A/B/C/Exploration 분류 10. 후보 최대 20명을 LLM Judge에 전달 11. LLM Judge 순위 결과를 검증/정규화 12. tier quota 기반 post-processing으로 최대 5명 선정 13. 부족하면 legacy category ranking으로 underfill 보충 14. worries, deliveryBatches, deliveries, moderationLogs를 transaction으로 저장 15. 답변/좋아요/moderation 이벤트로 experience profile과 signal 원장을 업데이트 16. Cron Job이 profile summary 재생성과 90일 decay를 주기적으로 수행

3. Ontology v1

매칭 알고리즘은 고정된 ontology v1을 사용한다. LLM이 임의로 만든 태그는 직접 매칭 점수에는 사용하지 않고, suggestedNewTags에만 보관한다.

분류 태그 제약
Topic 진로, 취업, 직장, 학업, 시험, 경제, 연애, 결혼, 가족, 인간관계, 육아, 건강, 외모, 군대, 미래, 일상 Concern Analyzer 결과에서 최대 3개
Emotion 불안, 우울감, 외로움, 자존감저하, 무기력, 좌절, 슬픔, 분노, 죄책감, 후회, 혼란, 부담감 최대 2개. 현재 retrieval score에는 직접 반영하지 않고 분석/기록에 사용
Desired Response 공감, 경험공유, 현실조언, 정보제공, 격려, 관점정리 최대 2개. answerStyle overlap에 사용
Situation 장기취준, 서류탈락, 면접실패, 이직고민, 직장적응, 상사갈등, 번아웃, 성적부진, 시험불안, 진로혼란, 휴학고민, 전공불만, 이별, 짝사랑, 연애갈등, 부모갈등, 친구갈등, 대인관계어려움, 경제부담, 미래불확실성, 건강염려, 외모고민, 군생활적응, 일상무기력 최대 3개. retrieval score에서 가장 높은 가중치

구현 파일: src/services/matching/server/ontology.ts

4. Experience Profile

experienceProfile은 사용자가 어떤 주제와 상황에서 답변 경험을 쌓았는지 나타내는 서버 소유 프로필이다. 클라이언트가 직접 수정할 수 없고, 온보딩/답변/좋아요/moderation/decay job에 의해 갱신된다.

필드 설명
profileStatus cold_start, light, validated, trusted. 현재 기본값은 cold_start이며 활동이 생기면 light로 승격된다.
topicScores Topic tag별 경험 점수. 온보딩 선택 주제는 초기값 1로 생성된다.
situationScores Situation tag별 경험 점수. 답변/좋아요 signal에서 쌓인다.
answerStyleScores Desired response tag별 답변 스타일 점수. 예: 공감, 현실조언, 정보제공.
topTopics, topSituations, topAnswerStyles 각 score map에서 상위 태그를 정규화해 저장한다. LLM Judge와 summary generation에 사용된다.
profileSummary LLM이 생성한 짧은 경험 요약. Matching Judge가 후보 맥락을 판단할 때 참고한다.
recentPositiveSignals 최근 긍정 signal source 목록. 현재 reply_created, like_received가 반영된다.
safetyPenalty moderation fail 등 안전 리스크 신호 누적값. trusted 판단 및 매칭 품질에 영향을 준다.

구현 파일: src/services/matching/server/experienceProfile.ts

5. 온보딩 초기화

사용자가 온보딩에서 선택한 관심사는 서버에서 experience topic으로 매핑된다. 최신 도메인 카테고리는 이미 새 ontology와 맞춰져 있으며, legacy 값은 도메인 정규화 단계에서 현재 카테고리로 변환된다.

입력 예시 저장 결과
["직장", "취업"] topicScores: { "직장": 1, "취업": 1 }, topTopics: ["직장", "취업"], profileStatus: cold_start

구현 파일: src/services/matching/server/interestTopicMapping.ts, src/services/userProfile/onboardingProfile.ts

6. Concern Analyzer

고민 작성 시 LLM Concern Analyzer가 원문을 experience ontology로 분석한다. 분석 결과는 worries.llmAnalysis에 저장되고, high risk 판단과 후보 검색에 사용된다.

출력 필드 용도
topicTags 후보의 topicScores와 overlap 계산
emotionTags 고민의 정서 맥락 기록. 현재 retrieval score에는 직접 반영하지 않음
situationTags 후보의 situationScores와 overlap 계산. 가장 높은 가중치
desiredResponse 후보의 answerStyleScores와 overlap 계산
riskLevel high이면 matching/delivery 중단
matchingBrief 30~60자, 한 문장. LLM Judge에 전달할 고민 요약 맥락
Analyzer 결과가 invalid이면 retry하고, 그래도 실패하면 fallback analysis를 사용한다. 따라서 LLM 분석 실패가 곧바로 고민 발행 전체 실패로 이어지지 않는다.

구현 파일: src/services/matching/server/concernAnalysis.ts, src/services/worryPublication/server/concernAnalysis.ts

7. High Risk Policy

Concern Analyzer가 riskLevel: high를 반환하면 매칭을 중단한다. 이 경로에서는 worries, deliveryBatches, deliveries를 생성하지 않는다.

riskLevel 처리
low 일반 매칭 진행
medium 현재 구현에서는 일반 매칭 진행. 추후 추가 moderation 정책을 붙일 수 있음
high risk_blocked 반환, delivery 생성 0개, moderationLogs.reasonCode = high_risk

사용자 안내에는 119/112, 자살예방상담전화 109, 정신건강위기상담 1577-0199가 포함된다.

구현 파일: src/services/worryPublication/server/riskPolicy.ts

8. 후보 Eligibility Policy

후보 검색 전 전체 사용자 pool에서 매칭 불가 사용자를 제외한다. 현재 repository는 운영 users 컬렉션을 넓게 스캔한 뒤 서버 정책으로 필터링한다.

제외 조건 설명
작성자 본인 candidate.uid === authorUid이면 제외
삭제/비활성/차단 계정 deleted, status: deleted, inactive, disabled이면 제외
봇 계정 uid가 bot_으로 시작하거나 isBot, type: bot이면 제외
수신 한도 초과 activeDeliveryCount >= 10이면 제외

구현 파일: src/services/matching/server/recipientPolicy.ts, src/services/matching/server/candidateRetrieval.ts

9. Retrieval Score

후보의 experience profile과 고민 분석 결과를 비교해 retrieval score를 계산한다. 이 점수는 LLM Judge에 넘길 후보의 1차 우선순위와 Tier 분류에 사용된다.

retrievalScore = 2 * topicOverlap + 3 * situationOverlap + 1 * answerStyleOverlap
항목 계산 방식 가중치 이유
topicOverlap 후보 topicScores key와 고민 topicTags의 교집합 수 큰 주제 일치. 기본 적합도
situationOverlap 후보 situationScores key와 고민 situationTags의 교집합 수 구체적 경험 일치. 가장 중요하므로 3점
answerStyleOverlap 후보 answerStyleScores key와 고민 desiredResponse의 교집합 수 답변 스타일 일치. 보조 신호

구현 파일: src/services/matching/server/candidateRetrieval.ts

10. Tier 분류

retrieval score와 profile status를 함께 사용해 후보를 Tier로 나눈다. Tier는 최종 post-processing quota에 직접 반영된다.

Tier 조건 의미
A retrievalScore >= 7이고 profileStatus가 validated 또는 trusted 강한 경험 일치 + 검증된 프로필
B retrievalScore >= 4 충분한 주제/상황/스타일 일치
C retrievalScore >= 1 약한 일치가 있는 후보
Exploration profileStatus === cold_start 경험 데이터가 부족한 신규 사용자. 제한적으로 노출
제외 cold start가 아니고 retrievalScore === 0 경험 일치가 없어 후보에서 제거

11. LLM Matching Judge

retrieval을 통과한 후보는 최대 20명까지 LLM Judge에 전달된다. Judge는 후보를 고민에 맞는 순서로 정렬하고, 각 후보에 대한 짧은 reason을 반환한다.

Judge 입력

  • 고민 분석 결과: topic, situation, desired response, matching brief
  • 후보 context: uid, tier, retrieval score, profile status, top topics/situations/answer styles, profile summary, helpedCount, safetyPenalty

Judge 제한

  • 입력 후보에 존재하는 candidateId만 반환해야 한다.
  • candidateId는 중복될 수 없다.
  • private, sensitive, demographic, identity trait를 추론하거나 사용하지 말아야 한다.
  • reason은 한국어 짧은 한 문장이어야 하며 내부 점수를 직접 언급하지 않는다.
  • invalid output이면 한 번 retry한다.

구현 파일: src/services/matching/server/llmJudge.ts, src/server/moderationProvider.ts

12. Post-processing Quota

LLM Judge가 순위를 주더라도 최종 선택은 tier quota를 적용한다. 이렇게 하면 특정 tier에 과도하게 치우치지 않고, cold start 사용자에게도 제한적인 탐색 기회를 줄 수 있다.

선택 순서 Tier 최대 수
1 A 최대 2명
2 B 1명
3 B 추가 1명
4 C 1명
5 A 남는 슬롯이 있으면 추가 1명
6 Exploration 남는 슬롯이 있으면 1명

최종 delivery target은 5명이다. 후보가 부족하면 선택 가능한 만큼만 반환하고, 발행/패스/rematch 단계에서 legacy fallback이 부족분을 보충한다.

구현 파일: src/services/matching/server/postProcessing.ts

13. Delivery 저장 구조

최종 선택된 recipient는 deliveries에 저장된다. experience matching으로 선정된 경우 llmMatch snapshot이 같이 저장된다.

필드 설명
selectionType matched 또는 legacy fallback의 random
matchOverlapCount experience recipient는 topic overlap 값, legacy recipient는 기존 category overlap 값
matchCategoriesSnapshot moderation category inference에서 나온 matching category snapshot
recipientInterestsSnapshot 전달 시점 수신자의 관심사 snapshot
llmMatch tier, LLM rank, reason, retrievalScore, topic/situation/answerStyle overlap 저장

14. Underfill Fallback

Experience matching 결과가 목표 수 5명을 채우지 못하면 기존 카테고리 기반 랭킹으로 부족한 슬롯을 채운다. 이 fallback은 초기 운영처럼 cold_start 유저가 많고 검증된 experience profile이 적은 상태에서 delivery 부족을 줄이기 위한 장치다.

  • experience matching으로 먼저 recipient를 선택한다.
  • 이미 선택된 uid는 fallback 후보에서 제외한다.
  • legacy rankMatchedHumanCandidates로 부족한 수만큼 보충한다.
  • 최종 recipient는 중복 없이 저장된다.

구현 파일: src/services/worryPublication/server/recipientSelection.ts

15. Pass 및 Rematch에서의 매칭

최초 발행뿐 아니라 pass replacement와 rematch due delivery에도 같은 experience matching 구조를 적용했다.

흐름 적용 방식
Pass replacement 사용자가 고민을 pass하면 대체 recipient를 experience matching으로 찾고, 부족하면 legacy fallback으로 보충한다.
Rematch 기존 delivery batch의 답변/패스 상태를 고려해 다음 round recipient를 experience matching으로 찾는다.

Rematch는 기존 PRD의 5-slot 정책과 round 제한을 유지한다. 이미 답변했거나 pass한 사용자, 기존 round에서 받은 사용자는 중복 delivery 대상에서 제외된다.

구현 파일: src/services/deliveries/passDelivery.ts, src/services/rematch/rematchDueDeliveries.ts, src/services/rematch/policy.ts

16. Experience Profile 학습 규칙

사용자 활동은 즉시 experience profile에 반영되고, 동시에 experienceSignals 원장에 저장된다. 즉시 반영은 매칭 품질을 빠르게 개선하기 위한 것이고, signal 원장은 90일 decay 재계산을 위한 기준 데이터다.

이벤트 signal source 가중치 반영 내용
답변 작성 성공 reply_created 0.5 원 고민의 topic/situation/desired response를 답변자 profile에 반영
답변 좋아요 수신 like_received 2 긍정 신호로 강하게 반영하고 helpedCount 증가
답변 moderation fail moderation 관련 signal score 가중치 없음 safetyPenalty 증가, profile summary 재검토 대상

활동 신호가 들어오면 experienceProfileDecayPending이 true가 되고, Cron Job이 이후 90일 기준 재계산을 수행한다.

17. Profile Summary 재생성

profileSummary는 LLM Judge가 후보의 경험 맥락을 빠르게 이해하도록 돕는 요약문이다. 매 activity마다 즉시 LLM을 호출하지 않고, 조건을 만족하면 job queue에 넣고 Cron Job이 처리한다.

재생성 조건 reason
이전 summary snapshot 대비 helpedCount +3 이상 helped_count_delta
topTopics가 이전 summary snapshot과 달라짐 top_topics_changed
마지막 summary update가 없거나 7일 이상 지남 stale_7d
중요 moderation 이벤트 발생 moderation_event

Internal route는 POST /api/internal/experience-profile-summaries/run이고, Render Cron Job은 npm run internal:profile-summary로 10분마다 실행된다.

18. 90일 Experience Decay

사용자의 오래된 경험이 영구적으로 매칭에 남지 않도록 최근 90일 signal만 재합산한다. 이 방식은 단순히 점수를 일정 비율로 깎는 것이 아니라, signal 원장에서 최근 90일 데이터만 다시 읽어 profile을 재구성한다.

  • 대상: users.experienceProfileDecayPending === true
  • 기본 batch limit: 50, route validation maximum: 100
  • 사용 signal: experienceSignals.uid === user uid이고 signalDate가 최근 90일 이내
  • 재계산 후 experienceProfileDecayPending을 false로 변경
  • 필요하면 profile summary job을 함께 enqueue

Internal route는 POST /api/internal/recalculate-experience-profiles이고, Render Cron Job은 npm run internal:decay로 하루 1회 실행된다.

19. 보안 및 운영 경계

  • 서버 소유 필드인 experienceProfile, profileStatus, decay 관련 필드는 클라이언트 직접 write가 금지된다.
  • experienceSignals와 experienceProfileSummaryJobs는 클라이언트 read/write 모두 금지된다.
  • Internal route는 Authorization: Bearer INTERNAL_JOB_SECRET이 없으면 401로 차단된다.
  • LLM API key는 코드에 저장하지 않고 Render 환경변수 OPENAI_API_KEY로 주입한다.
  • 테스트는 provider dependency injection과 mock을 사용해 실제 LLM 호출 없이 검증한다.

22. 남은 QA 포인트

알고리즘과 운영 자동화는 반영되었지만, 일반 고민 작성은 실제 사용자에게 delivery가 갈 수 있으므로 자동 smoke test로 실행하지 않았다. 아래 항목은 앱 화면에서 수동 QA로 확인하는 것이 안전하다.

QA 항목 확인할 데이터
