Qling 매칭 알고리즘 구현 업데이트

작성일: 2026-06-04 / 기준 문서: matching.md, docs/PRD.md

구현 및 테스트 완료

1. 전체 요약

matching.md에 정리된 경험 기반 매칭 알고리즘을 기존 서버 코드에 단계적으로 반영했다. 기존 단순 카테고리/랜덤 중심 매칭에서, 고민 분석, 경험 프로필, 후보 검색, LLM Judge, tier 기반 후처리, pass/rematch 대체 매칭, 프로필 학습, high risk 차단, profile summary 재생성, 90일 decay까지 포함하는 구조로 확장했다.

2. 개발 규칙 및 문서 정리

  • 루트 문서와 실제 코드 구조를 확인해 개발 규칙과 코드 구조를 codex.md로 정리했다.
  • docs/PRD.md는 source of truth로 유지했고 수정하지 않았다.
  • .env.example에 필요한 환경변수 키 이름만 추가했다.
  • 실제 API 키는 코드나 커밋 대상 파일에 넣지 않는 방향으로 유지했다.

3. 매칭 온톨로지 및 Concern Analysis

  • 경험 기반 매칭용 ontology v1을 추가했다.
  • topic, emotion, situation, desired response tag를 정규화하는 구조를 추가했다.
  • 고민 발행 시 LLM concern analysis를 수행하고 worries.llmAnalysis에 저장하도록 연결했다.
  • LLM provider 실패나 invalid output 발생 시 fallback concern analysis를 사용해 발행 자체가 중단되지 않도록 했다.

주요 파일:

  • src/services/matching/server/ontology.ts
  • src/services/matching/server/concernAnalysis.ts
  • src/services/worryPublication/server/concernAnalysis.ts
  • src/server/moderationProvider.ts

4. Experience Profile 저장 및 백필

  • users.profileStatus와 users.experienceProfile 구조를 추가했다.
  • 온보딩 저장 시 기존 관심사 데이터를 experience topic으로 보수적으로 매핑하도록 했다.
  • 기존 유저 대상 백필 스크립트를 추가했다.
  • 실제 Firestore 백필을 실행해 기존 활성 유저의 누락 필드를 채웠고, 백필 후 누락 유저가 0명인 것을 확인했다.

주요 파일:

  • src/services/matching/server/experienceProfile.ts
  • src/services/matching/server/interestTopicMapping.ts
  • src/services/userProfile/onboardingProfile.ts
  • src/services/userProfile/firestoreRepository.ts
  • scripts/backfillExperienceProfiles.ts

5. 후보 검색 및 Tier 분류

  • 후보 검색 점수식을 구현했다: 2 * topic_overlap + 3 * situation_overlap + 1 * answerStyle_overlap.
  • Tier A/B/C/Exploration 분류를 구현했다.
  • 삭제, 비활성, 봇, active delivery limit 초과 유저를 제외하도록 했다.
  • cold start 유저는 Exploration으로 분류해 별도 quota에서만 사용되도록 했다.

주요 파일:

  • src/services/matching/server/candidateRetrieval.ts
  • src/services/matching/server/recipientPolicy.ts

6. LLM Judge 및 후처리

  • 후보 최대 20명을 LLM Judge에 넘겨 적합도 순위를 받는 구조를 추가했다.
  • LLM Judge 결과는 candidate id dedupe, unknown candidate 제거, invalid output retry를 거친다.
  • 후처리에서 최종 delivery 5명을 tier quota에 따라 선택한다.
  • 선택 결과는 deliveries.llmMatch에 snapshot으로 저장한다.
  • 테스트에서는 mock provider를 사용해 실제 API 호출 없이 검증한다.

주요 파일:

  • src/services/matching/server/llmJudge.ts
  • src/services/matching/server/postProcessing.ts
  • src/services/matching/server/experienceRecipientSelection.ts
  • src/server/moderationProvider.ts

7. 최초 발행 매칭 적용 및 Underfill Fallback

  • 고민 발행 시 기존 초기 전달 로직을 경험 기반 매칭으로 교체했다.
  • 경험 기반 매칭 결과가 5명 미만이면 기존 legacy 랭킹으로 부족한 슬롯을 보충하도록 했다.
  • 이 fallback으로 cold start 유저가 많은 초기 운영 상태에서도 delivery underfill 위험을 줄였다.

주요 파일:

  • src/services/worryPublication/server/publishWorry.ts
  • src/services/worryPublication/server/recipientSelection.ts

8. Pass 및 Rematch 매칭 적용

  • pass replacement 후보 선정에 경험 기반 매칭을 적용했다.
  • rematch due deliveries에도 경험 기반 매칭과 LLM Judge를 연결했다.
  • 경험 매칭 결과가 부족하면 legacy fallback으로 보충해 전달 수 부족을 방지했다.
  • replacement delivery에도 llmMatch snapshot이 저장되도록 했다.

주요 파일:

  • src/services/deliveries/recipientSelection.ts
  • src/services/deliveries/passDelivery.ts
  • src/services/rematch/policy.ts
  • src/services/rematch/rematchDueDeliveries.ts

9. High Risk 처리

  • llmAnalysis.riskLevel === "high"인 고민은 매칭과 배송 생성을 중단하도록 했다.
  • 사용자에게 안전 안내 메시지와 전문기관 안내를 반환한다.
  • worries, deliveryBatches, deliveries는 생성하지 않는다.
  • moderationLogs에는 reasonCode: high_risk로 기록한다.
  • route 응답은 기존 rejected와 유사하게 HTTP 200으로 내려가며 내부 targetId는 제거한다.

주요 파일:

  • src/services/worryPublication/server/riskPolicy.ts
  • src/services/worryPublication/server/publishWorry.ts
  • src/server/worryRoutes.ts

10. Experience Profile 학습

  • 답변 작성 시 concern tag 기반으로 topicScores, situationScores, answerStyleScores에 0.5를 반영한다.
  • 좋아요 수신 시 같은 score에 2를 반영하고 helpedCount를 증가시킨다.
  • 답변 moderation fail 시 safetyPenalty를 증가시킨다.
  • 이벤트 발생 시 cold_start 프로필은 light로 승격한다.

12. 90일 Experience Decay

  • 정확한 decay를 위해 experienceSignals 원장 컬렉션을 추가했다.
  • 답변 작성, 좋아요 수신, 답변 moderation fail 시 signal을 dual-write한다.
  • 기존 experienceProfile 즉시 업데이트는 유지해 job 실행 전 매칭 품질 저하를 막았다.
  • experienceProfileDecayPending 유저를 대상으로 최근 90일 signal만 재합산한다.
  • 90일이 지난 signal은 재계산에서 제외된다.
  • 재계산 후 experienceProfileDecayPending을 false로 돌리고 experienceProfileRecalculatedAt을 기록한다.

주요 파일:

  • src/services/matching/server/experienceSignals.ts
  • src/services/matching/server/experienceDecay.ts
  • src/server/experienceDecayRoutes.ts

Internal route:

  • POST /api/internal/recalculate-experience-profiles
  • INTERNAL_JOB_SECRET 필요

16. 남은 운영 작업

코드에는 Render Cron Job에서 바로 실행할 수 있는 npm 명령을 추가했다. Render 대시보드에서 아래 cron job 2개를 등록해야 자동 처리된다.
  • 환경변수: QLING_INTERNAL_BASE_URL=https://qling-hangyeol-hyu.onrender.com
  • 환경변수: INTERNAL_JOB_SECRET는 web service와 cron job에 같은 값으로 설정한다.
  • Decay cron command: npm run internal:decay
  • Profile summary cron command: npm run internal:profile-summary
  • 권장 schedule: summary는 10분마다 */10 * * * *, decay는 하루 1회 0 18 * * * UTC 기준으로 등록한다.
  • 온보딩 UI의 새 matching tag 입력 화면은 다른 개발 파트에서 반영 예정이며, 반영 후 저장값 연동만 확인하면 된다.

17. Cron 실행 검증 보강

  • scripts/runInternalJob.ts의 실행 로직을 src/server/internalJobRunner.ts로 분리했다.
  • Render Cron Job 명령은 기존처럼 npm run internal:decay, npm run internal:profile-summary를 사용한다.
  • 테스트에서는 fetch provider를 mock으로 주입해 실제 API 호출 없이 내부 route 호출 형식, Bearer 인증 헤더, JSON body, 실패 응답 처리를 검증한다.
  • 성공/실패 로그에 INTERNAL_JOB_SECRET 값이 노출되지 않는 조건을 테스트로 고정했다.

18. 주의 사항

  • API key는 절대 커밋하면 안 된다.
  • LLM 관련 테스트는 provider DI/mock 구조로 되어 있어 실제 API 호출 없이 검증한다.
  • docs/PRD.md는 수정하지 않았다.
  • 실제 배포 전 Firestore rules 배포와 Render 환경변수 확인이 필요하다.
